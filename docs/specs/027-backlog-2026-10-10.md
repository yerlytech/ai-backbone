# 027 — The backlog of 2026-10-10, as one batch

## What

Every open line of `docs/backlog.md` (8 on 2026-10-10) is built in one
attended session and carried through the gate as one version. Rust build
output stops filling the disk, a build waits its turn in a real queue, a
save stops at the first cheap check that fails and says what ran, and three
small gaps close. The backlog is empty when it lands.

## Why

The maintainer asked on 2026-10-10: "windows ihtiyacı olan kalsın ...
diğerlerini tamamlayalım bu oturumda" (leave the Windows one, finish the
others in this session). Two of the lines cost real hours: a Mac's disk fell
to 2.7 GB free under Rust build output, and a save found a Turkish word only
after a ten-minute suite, twice.

## The lines this spec takes

All of them; the routine skips them while this spec is open.

**Rust build output** (`core.just`, a new `.ai-backbone/buildtrim.py`)

1. n-2cd44d and n-7b8c9b, one design. A Rust project's build folder gets a
   soft cap, 60 GB by default (`git config ai-backbone.build-cap`, per
   project or `--global`; `off` turns it off). Over the cap, the pieces
   written longest ago are removed until the folder is at 75% of it. A piece
   is one compiled unit: everything in `deps/`, `build/`, `.fingerprint/`
   that carries the same hash, removed together; an `incremental/` folder is
   a piece of its own. Never removed: anything written in the last 6 hours,
   the top-level files of a profile (the programs a person runs), and every
   piece of a profile whose cargo lock is held. Under 15% free disk the cap
   is halved. Only a folder cargo made (`CACHEDIR.TAG` and
   `.rustc_info.json` at its root) is ever touched.
   - It runs by itself in the background from `_build-wait`, which every
     Rust build passes, at most once an hour per folder, never on CI, and
     writes one line per run to a log in the folder; it never fails or
     holds a build. Nothing goes while cargo, rustc or rustdoc runs (found
     in review: cargo lets go of its locks when compiling ends, and a
     running `cargo test` still needs `deps/`); the background run waits
     for a quiet moment, an hour at most.
   - `just trim-build` runs it now and says what it removed.
   - `just session-start` warns when this disk has less than 10% free.
2. n-0db9ff: `_build-wait` becomes a queue. Each waiting build takes a
   ticket under the user's cache folder; only the oldest ticket goes, the
   next one only after the last start had a moment to show up. The 20-minute
   limit counts from when a ticket reaches the front, so waiters go one by
   one, never all at once. A ticket whose waiter has died is dropped.

**`just save`** (`core.just`)

3. n-98c69c and n-bf44a6, one change. The save runs the checks itself,
   stopping at the first one that fails (`prek run --fail-fast`), then the
   commit-message checks, then commits without running them twice. A check
   that fixes files is retried until nothing more changes (up to five
   times). A ten-minute suite listed last no longer runs when a cheap check
   above it has already failed. After a save, one line says how many checks
   passed and names the ones that had nothing to check; the full output of
   the last saves is kept in `.git/ai-backbone-checks.log`. A project whose
   hooks are not installed saves as before. The seed's
   `.pre-commit-config.yaml` says that the checks run in the order written,
   so a slow one goes last.

**Small**

4. n-5332d9: `.claude/worktrees/` in the template's `.gitignore`.
5. n-9f9be8: `upstream.py` reads `hf:owner/name`, a Hugging Face model
   pinned by its commit: newer commits are "newer", the pin's date is its
   commit's, and the local copy is looked for in the Hugging Face cache.
6. n-303cba: the session skill says what an agent does when its context
   nears the model's limit: finish the task in hand, write the handover into
   the day's journal, save, tell the maintainer the next step belongs in a
   new chat, and stop. It does not compact on its own.

## Measured

- prek 0.5.5: `prek run --fail-fast` runs hooks in the order written and
  stops at the first failure; a fixer that changes a file fails, so the next
  fixer is reached only on the next run. `prek run --stage commit-msg
  --commit-msg-filename F` runs the message checks alone.
- cargo 1.98.1: with a library's `.rlib`, its fingerprint or its `build/`
  folders deleted, the next build rebuilds them and runs. During a build
  `.cargo-build-lock` and `.cargo-artifact-lock` are held (an `flock` from
  another process is refused), and free after.
- Hugging Face: `api/models/<owner>/<name>/commits/main` lists commits
  newest first, each with `id`, `title` and `date`; an unknown model is 401.

## Not doing

- Trimming another language's build output. The layout and the lock are
  cargo's; another layer gets it when one asks.
- A cap per machine across projects. A cap per folder is what worked on the
  machine the lines came from.
- Trimming on Windows. cargo locks there with LockFileEx, which nobody has
  measured against Python's locks, so every profile counts as busy and
  nothing goes; the disk warning still holds.
- Spec 020's last line (a real Windows machine): still open, by the
  maintainer's word.
